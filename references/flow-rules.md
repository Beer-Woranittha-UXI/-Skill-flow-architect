## 1. รูปทรงกับความหมาย (ISO 5807)

| สัญลักษณ์ | รูปร่าง | ความหมาย |
|---|---|---|
| Start/End (Terminator) | วงรี | จุดเริ่มต้นและจุดสิ้นสุด |
| Process | สี่เหลี่ยมผืนผ้า | การกระทำหรือขั้นตอน (ใช้บ่อยที่สุด) |
| Decision | สี่เหลี่ยมข้าวหลามตัด | คำถามที่ตอบได้ เช่น Yes/No |

**สีไม่ใช่ตัวบอกประเภท — รูปทรงบอก** ถ้าต้องพึ่งสีเพื่อรู้ว่ากล่องนี้คืออะไร แปลว่าเลือกรูปทรงผิด

| code | กฎ |
|---|---|
| `S1` | flowchart ทั่วไปมี Start 1 จุดและ End 1 จุด — หลายจุดใช้กับกระบวนการซับซ้อนเท่านั้น |
| `S2` | ต้องมี End — flow ที่ไม่บอกว่าจบที่ไหน ส่งต่อ dev ไม่ได้ |
| `S9` | Process เขียนเป็นวลี "กริยา + กรรม" ยาวราว 3–5 คำต่อกล่อง เช่น "ส่งอีเมลยืนยัน" |
| `S6b` | ข้อความลงท้าย "ใช่หรือไม่?" แต่ไม่ใช่ Decision = ใช้รูปทรงผิด |
| `S10` | ทุก node ต้องมีเส้นออก ยกเว้น End / Link To Flow |
| `S10b` | เดินจาก Start ต้องถึงทุก node — node ลอยคือ flow ที่ยังไม่จบความคิด |
| `S8b` | ข้อความเดียวกัน = node เดียวกัน ใช้ชื่อเรียกให้เหมือนกันทั้ง flow |
| `S14` | เส้นย้อนกลับ (`..>`) ชี้ไปที่ **หน้าจอ** (PAGE/START) เท่านั้น — ข้าวหลามตัด / Link To Flow / END ไม่ใช่หน้าจอ |

### เส้นย้อนกลับชี้ไปไหนได้ (`S14`)

"ย้อนกลับไปหน้าก่อนหน้า" เป็นการกระทำของ **ผู้ใช้** (กดปุ่มย้อนกลับ / ปัดกลับ) ปลายทางจึงต้องเป็น
สิ่งที่ผู้ใช้มองเห็นได้ คือหน้าจอ ส่วนข้าวหลามตัดเป็นเงื่อนไขที่ **ระบบ** เช็คเองเบื้องหลัง
ไม่มีหน้าจอให้กลับไป ถ้าวาดย้อนกลับเข้าข้าวหลามตัด คนอ่าน flow จะเข้าใจว่ามีหน้าจอ
"เช็คยอดเงิน" อยู่จริง แล้ว dev จะสร้างหน้าที่ไม่ควรมี

```
ผิด : [หน้าชำระเงิน] ..> <ยอดเงินพอ ใช่หรือไม่?>
ถูก : [หน้าชำระเงิน] ..> [หน้าตะกร้า]        ← หน้าจอที่ผู้ใช้เห็นก่อนหน้านี้จริง ๆ
```

ถ้ากดย้อนกลับแล้วระบบต้องเช็คเงื่อนไขใหม่ ให้เขียนเป็นเส้นย้อนกลับไป "หน้าจอ" ก่อน
แล้วให้หน้าจอนั้นมีเส้นปกติวิ่งเข้าข้าวหลามตัดตามปกติ — เงื่อนไขจะถูกเช็คซ้ำเองตาม flow

## 2. Decision — กฎเมื่อวางต่อกัน

| code | กฎ | เหตุผล |
|---|---|---|
| `S3` | ทุก Decision ต้องมีทางออก 2 ทาง | ทางออกเดียวไม่ใช่เงื่อนไข มันคือขั้นตอน |
| `S4` | **ทุกทางออกต้องมีป้าย** (Yes/No, True/False หรือเงื่อนไขอย่าง ">1,000 บาท") | เส้นไม่มีป้าย = คนอ่านเดา |
| `S5` | ทางออกมีได้ **2 ทางเท่านั้น** เงื่อนไขที่เหลือให้แยกเป็น Decision อันถัดไปต่อกัน | ข้าวหลามตัด 3 ทางขึ้นไปอ่านไม่ออก และแตกเป็นชั้น ๆ ทดสอบง่ายกว่า |
| `S7` | หนึ่งข้าวหลามตัด ถามหนึ่งเรื่อง — เจอ "และ/หรือ" ในคำถามให้แยก | "A และ B หรือ C?" ทำให้ทดสอบไม่ได้ว่าพังที่เงื่อนไขไหน |
| — | เงื่อนไขที่ตอบได้หลายค่า (เช่น ยอดเงิน ต่ำ/ปกติ/สูง) เขียนเป็น Decision ต่อกันเป็นชั้น: `<ยอดต่ำกว่าขั้นต่ำ ใช่หรือไม่?>` → No → `<ยอดเกินวงเงิน ใช่หรือไม่?>` | ทุกชั้นตอบ Yes/No ได้ และ QA ไล่เทสต์ได้ทีละเงื่อนไข |
| `S6` | คำถามจบด้วย **"ใช่หรือไม่?"** เท่านั้น (ตาม template ของ Amm) | คำถามชัด ไม่ใช่แค่ "ตรวจสอบ" · คำลงท้ายเดียวกันทั้งระบบทำให้กวาดตาหาเงื่อนไขได้เร็ว |
| `S8` | ชื่อคำถามชัดเจนและไม่ซ้ำกัน (ISO 5807) | ซ้ำกันแล้วแยกไม่ออกว่าเป็นคนละเงื่อนไข ถ้าเป็นเงื่อนไขเดียวกันให้โยงกลับ node เดิม |
| `S11` | ป้ายทางออกใช้ได้แค่ **Yes** กับ **No** — True/False หรือ ต่ำ/ปกติ/สูง ใช้ไม่ได้ | consistency ข้าม flow ทั้งระบบ · ป้ายหลายแบบทำให้ dev อ่านเงื่อนไขไม่ตรงกัน |
| `S13` | เส้นที่ **ออก** จากข้าวหลามตัดต้องมีป้ายทุกเส้น (Yes / No / เงื่อนไข) | ข้าวหลามตัดมีหน้าที่เดียวคือแยกทาง ไม่ใช่ขั้นตอน |

**ข้าวหลามตัดหนึ่งอันมีเส้นออก 2 เส้นเท่านั้น: Yes กับ No** ส่วนเส้นที่วิ่ง *เข้า* ทุกเส้น
(รวมเส้นย้อนกลับ) มารวมที่ **ปลายซ้าย** ของข้าวหลามตัดจุดเดียว — จะได้อ่านออกทันทีว่า
"เข้าทางซ้าย ตัดสินใจ แล้วออกสองทาง" ไม่ต้องไล่ว่าเส้นไหนเข้าเส้นไหนออก

รูปแบบมาตรฐานที่ทีมใช้ — **flow เดินจากซ้ายไปขวา** Yes ไหลต่อไปทางขวา No แตกลงล่าง:

```
[กดซื้อ] ─→ <ล็อกอินแล้ว ใช่หรือไม่?> ──Yes──→ <ยืนยันตัวตน (KYC) แล้ว ใช่หรือไม่?> ──Yes──→ ...
                    │No                                  │No
                    ▼                                     ▼
            [หน้าเข้าสู่ระบบ] ─────┘ (กลับเข้าปลายซ้าย)  [หน้า KYC] ─────┘
```

## 3. Geometry — ตัวเลขที่ล็อกไว้

`render_flow.py` บังคับให้เองทั้งหมด ไม่ต้องจำ แต่ต้องรู้ว่าถ้าเลขเปลี่ยนคือผิด

| code | ค่า | ของ |
|---|---|---|
| `G5` | padding 16 (บน-ล่าง) / 24 (ซ้าย-ขวา), corner radius 16 | กล่องข้อความ / สี่เหลี่ยมผืนผ้า |
| `G4` | Diamond เป็น **สี่เหลี่ยมจัตุรัส** ขนาดเท่ากันทุกอันใน flow เดียว — ข้อความเยอะให้ยืดแบบ scale ทั้งชุด ห้ามยืดเป็นทรงแบน, radius 16 | สี่เหลี่ยมข้าวหลามตัด |
| `G2` | ป้าย Yes / No ห่างจากจุดที่เส้นวิ่งออก **100px** | ทางออก Diamond |
| `G1` | ทุกเส้นยาวเริ่มต้นที่ **500px** นับจากจุดที่เส้นวิ่งออก | ทุกเส้น |
| `G6` | **ทางเข้า** ของเส้นรูปแบบเดียวกันใช้จุดเดียวกันได้ — เส้นคนละรูปแบบต้องเกาะ **ด้านอื่นของกล่อง** | จุดเชื่อม |
| `G9` | **ทางออก** Yes กับ No ต้องออก **คนละด้าน** (Yes ไปขวา · No ลงล่าง) | Diamond |
| — | **ยกเว้น:** ทางเข้าข้าวหลามตัดของเส้นทึบรวมที่ปลายซ้ายเสมอ ไม่นับเป็นการชนกัน | Diamond |
| `G3` | เส้นวิ่งผ่านพื้นที่ว่างเท่านั้น — แตะได้แค่กล่องต้นทางกับปลายทางของตัวเอง | เส้น |
| `G7` | ป้ายวางบนพื้นที่ว่าง | ป้าย |
| `G8` | ทุกเส้นอยู่ในกรอบ canvas (ไม่ถูกตัดหาย) | เส้น |

"รูปแบบเส้น" นับตามหน้าตาที่ตาเห็น ไม่ใช่ความหมาย — มี 3 รูปแบบ

| รูปแบบ | เส้นที่นับรวมกัน | จุดเชื่อม |
|---|---|---|
| ทึบ | เส้นปกติ · Yes · No | ใช้จุดเดียวกันได้ (เป็นจุดรวมเส้น) |
| ประน้ำเงิน | เส้นย้อนกลับ | ต้องอยู่ด้านอื่นของกล่อง |
| ประเหลือง | Permutation | ต้องอยู่ด้านอื่นของกล่อง |

กฎนี้ใช้กับ **ทางเข้า** เท่านั้น — ทุกเส้นที่วิ่งเข้ากล่องหมายถึง "ไหลเข้ากล่องนี้" เหมือนกันหมด
จึงรวมจุดกันได้ถ้าหน้าตาเส้นเหมือนกัน

**ทางออกคิดคนละแบบ** — เส้นแต่ละเส้นที่ออกจากกล่องพาไปคนละที่ ถ้าซ้อนจุดกันจะอ่านไม่ออกว่า
เส้นไหนไปไหน โดยเฉพาะข้าวหลามตัดที่ Yes กับ No ต้องแยกออกจากกันให้เห็น (กฎ `G9`)
ค่าตั้งต้น: **Yes ออกทางขวาไปต่อ · No ลงล่างแตก branch**

ทิศทางของ flow: **ซ้าย → ขวา** ขั้นถัดไปอยู่ขวา (ออกด้านขวา เข้าด้านซ้าย) branch แตกลงล่าง
เส้นทุกเส้นเป็นมุมฉากมนรัศมี 16 ไม่มีเส้นเฉียง — เส้นเฉียงทำให้ไล่สายตาแล้วหลุด
เส้นแนวนอนวิ่งในช่องว่างระหว่าง lane เส้นแนวตั้งวิ่งในช่องว่างระหว่างขั้น จึงไม่ทับกล่อง

## 4. การเขียนข้อความ (copy)

ก่อนแก้ข้อความในกล่อง ให้ดู writing rules ของโปรเจกต์นั้นก่อน — ดู
[style-guide.md](style-guide.md) §เชื่อมกับ writing skill ของโปรเจกต์
ถ้าโปรเจกต์ไม่มีกฎของตัวเอง ใช้ค่าตั้งต้นนี้

- **Process** = กริยา + กรรม 3–5 คำ, ชื่อหน้าใช้ชื่อที่ทีม dev เรียกจริง
- **Decision** = คำถามเต็มประโยค จบด้วย "ใช่หรือไม่?"
- **Link To Flow** = "Flow <ชื่อ flow ปลายทาง>" ให้ตามไปเปิดใบนั้นได้
- **Permutation** = ลิสต์เคสคั่นด้วย `/` ไม่ต้องเขียนเป็นประโยค
- ใช้ภาษาที่ผู้ใช้เห็นบนหน้าจอจริง — flow อ่านด้วยสายตาผู้ใช้ ไม่ใช่สายตาระบบ

## 4.5 ที่มาของกล่อง — ใครคิด

ทุกบรรทัดใน `.flow` ที่มาจาก **ข้อเสนอของ AI ที่ดีไซเนอร์อนุมัติแล้ว** ต้องมีคอมเมนต์
`# [AI-xx] เหตุผล` ต่อท้าย (ตาม `review-protocol.md` §4) — parser จะเก็บไปใส่
`.meta.json` เป็น `author` / `ai_id` / `note` แล้ว `render_flow.py` พิมพ์เป็นบล็อก
**"ที่มาของ flow"** ใต้ผังใน `.html` บรรทัดที่ไม่มีคอมเมนต์นี้ถือเป็นของดีไซเนอร์เสมอ

| code | กฎ | เหตุผล |
|---|---|---|
| `A1` | กล่องที่มาจากข้อเสนอของ AI ต้อง **ไม่เกิน 40%** ของทั้งใบ | เกินกว่านี้แปลว่าใบนี้เป็น flow ของ AI ไม่ใช่ของดีไซเนอร์ — ผิดข้อบังคับของสกิล ให้ถอยไปคุยโครงก่อน (`SKILL.md` Step 4) |
| `A2` | เส้นที่มาจากข้อเสนอของ AI ต้องถูกไล่ดูว่าอนุมัติครบแล้ว | เส้นเปลี่ยนความหมายของ flow ได้พอ ๆ กับกล่อง แต่คนมักไล่ดูแค่กล่อง |

> **ทำไมไม่ทำเป็นสีบนผัง** — `style-guide.md` ล็อกไว้ว่าทั้งใบมีสีเน้นได้แค่ Yes/No
> กับเส้น Permutation และเส้นประจองไว้ให้กล่อง note แล้ว ที่มาของกล่องจึงไปอยู่ใน
> บล็อกแยกใต้ผัง ไม่แตะ geometry และไม่กินสีที่เหลือ

## 4.6 เคสพิเศษที่ยังไม่ปิด — edge case · error state · empty state

เครื่องบอกได้แค่ว่า **หน้าไหนยังไม่มีเคสพิเศษผูกอยู่** (`PERM <id> <เคส>`)
ส่วนเคสที่ขาดคืออะไร เป็นงานของ §4 ในรายงาน — เครื่องไม่รู้จักโปรดักต์

| code | กฎ | เหตุผล |
|---|---|---|
| `E1` | ทั้งใบต้องมีอย่างน้อย 1 หน้าที่ผูกเคสพิเศษไว้ | flow ที่ไม่มีเคสพิเศษเลยแปลว่ายังไม่ได้ไล่ ไม่ใช่ว่าไม่มี — dev จะไปเจอเองตอน build |
| `E2` | หน้าที่เป็นปลายทางของเส้น `No` ควรมีเคสพิเศษ | ผู้ใช้ถูกส่งมาหน้านี้เพราะเงื่อนไขไม่ผ่านอยู่แล้ว มักมีทั้ง *ทำไม่สำเร็จซ้ำ* และ *ข้อมูลว่าง* ซ้อนอีกชั้น |

`E1` เป็น R1 (ควรแก้) · `E2` เป็น R2 (ข้อสังเกต — ดีไซเนอร์ตัดสินใจ)
บรรทัดสรุปท้ายการตรวจจะบอกเสมอว่า **เคสพิเศษ N/M หน้า** แม้ไม่มีข้อผิด

**3 หมวดที่ต้องกวาดให้ครบก่อนส่ง**

| หมวด | ถามว่า |
|---|---|
| edge case | ทำสำเร็จแต่เงื่อนไขไม่ปกติ — ของหมด เกินโควตา หมดเวลา ถูกคนอื่นตัดหน้า |
| error state | ทำไม่สำเร็จ — เน็ตหลุด ระบบล่ม ตัดเงินไม่ผ่าน กดซ้ำ |
| empty state | เข้ามาแล้วไม่มีข้อมูลให้ดู — ยังไม่เคยใช้ ลบหมดแล้ว ค้นไม่เจอ |

## 4.7 เกณฑ์รับร่าง และการวนรีวิว

| code | กฎ | เหตุผล |
|---|---|---|
| `D1` | ร่างต้องมีครบ 4 ข้อถึงจะเริ่มตรวจ — จุดเริ่ม 1 + จุดจบ ≥ 1 · step ระหว่างทาง ≥ 3 · decision point ≥ 1 · `GOAL` 1 ประโยค | ตั้งใจให้เบา ต่ำกว่านี้คือยังไม่ได้คิด สูงกว่านี้คนจะเลี่ยงไม่ร่าง · ทำให้ Gate วัดได้ ไม่ใช่ความรู้สึก |
| `V1` | ทุกจุดตัดสินใจต้องถูกปิดด้วย `CLOSED <id> <เหตุผล>` ก่อนถือว่ารีวิวจบ | รีวิวหลายรอบโดยไม่จดว่าปิดอะไรไปแล้ว = รอบหน้ายกมาถามซ้ำ ดีไซเนอร์เสียเวลาตอบเรื่องเดิม |
